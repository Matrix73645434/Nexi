# Nexlock — архитектурное предложение (v0.1, на согласовании)

Статус: **утверждено владельцем (ред. 2)**, решения — в разделе 13.
Исходная концепция и ТЗ — от владельца проекта; этот документ — ответ на «Первое задание».

---

## 1. Как я понимаю задачу

Nexlock = два канала связи в одном приложении:

| | Интернет-мессенджер | Radio Chat |
|---|---|---|
| Транспорт | TLS → сервер Nexlock → адресат | Телефон → BLE → устройство Nexlock (ESP32 + LoRa) → эфир → устройство → BLE → телефон |
| Нужен интернет | да | нет (только для первичной привязки устройств и обмена ключами) |
| Адресация | UID | DID |
| Шифрование | E2EE (Signal Protocol) поверх TLS | Отдельная компактная AEAD-схема (кадр LoRa ≤ 240 байт) |

Ключевой принцип: **сервер — «слепой» ретранслятор**. Он знает, кто кому пишет, но не видит содержимое сообщений. Radio Chat вообще не проходит через сервер.

## 2. Технологический стек

### Мобильное приложение — React Native + Expo (dev build) + TypeScript

Почему:

1. **Один язык на всю программную часть** — TypeScript в приложении, на сервере и в общем пакете протокола (типы сообщений, схемы валидации, кодек радиокадра). Меньше рассинхронизации форматов между клиентом, сервером и (через спецификацию) прошивкой.
2. **BLE к ESP32** — `react-native-ble-plx` (зрелая библиотека, Android + iOS). Требует dev build, Expo Go не подойдёт — это нормально.
3. **Дизайн «космос + червоточина»** — `@shopify/react-native-skia` (GPU-рисование сетки/свечения) + `react-native-reanimated` (анимации на UI-потоке).
4. **Безопасное хранилище ключей** — `expo-secure-store` (Android Keystore / iOS Keychain).
5. **Навигация** — `expo-router` (файловая маршрутизация, удобно ложится на список экранов из ТЗ).
6. **Push** — `expo-notifications` (FCM / APNs).

Альтернатива — Flutter (`flutter_blue_plus`, отличная графика). Проигрывает только в том, что сервер и общий протокол придётся вести на втором языке. Если предпочитаете Flutter — архитектура ниже не меняется.

### Сервер — Node.js (Fastify) + PostgreSQL + Redis

- **Fastify + WebSocket** — REST для авторизации/профилей, WebSocket для доставки сообщений и статусов в реальном времени.
- **PostgreSQL** — пользователи, идентификаторы, устройства, сессии, очередь недоставленных зашифрованных конвертов.
- **Redis** — rate limit, TTL одноразовых кодов, presence соединений.
- **SMS-провайдер** — через интерфейс `SmsProvider` (конкретный провайдер выбирается позже: SMS.ru / SMSC / Twilio и т.д.). В разработке — `ConsoleSmsProvider`, **явно помеченная заглушка**, печатает код в лог сервера.
- Запуск локально — `docker compose` (Postgres + Redis + сервер).

### Криптография (никаких самописных алгоритмов)

- **Интернет-чаты:** Signal Protocol через официальную `libsignal` (Signal Foundation; есть официальные Java/Kotlin и Swift-обёртки → подключаем нативным Expo-модулем).
- **Radio Chat:** `libsodium` (на телефоне — `react-native-libsodium`): X25519 + ChaCha20-Poly1305-IETF, Ed25519 для подписи устройств.
- **Прошивка:** libsodium / mbedTLS (входит в ESP-IDF) — те же примитивы.
- **Сервер:** только хэши (HMAC-SHA-256 для OTP, SHA-256 для refresh-токенов), TLS 1.3 на входе.

### Прошивка устройства — PlatformIO, ESP-IDF/Arduino, C++

- ESP32 WROOM ↔ телефон: **BLE (GATT)**. Bluetooth Classic не подходит: iOS не даёт приложениям SPP без MFi.
- ESP32 ↔ E22-400T30D: UART + пины M0/M1/AUX (модуль сам делает LoRa-модуляцию на SX1268).

## 4. Система идентификаторов

*Утверждено владельцем (ред. 2).*

| ID | Что это | Формат | Кто выдаёт | Публичный? |
|---|---|---|---|---|
| **UID** | ID пользователя. Выдаётся автоматически при регистрации; **выбрать, изменить или переписать нельзя**. Единственный способ найти пользователя. | `NX-XXXX-XXXX` (Crockford Base32, 40 бит случайности, без похожих символов `I L O U`) | Сервер при регистрации, случайно (не по порядку — чтобы нельзя было перебрать или узнать число пользователей) | Да — в профиле, для поиска |
| **DID** | ID физического устройства Nexlock. | `D-` + Base32 от первых 10 байт SHA-256(Ed25519 public key устройства) | Выводится из ключа, регистрируется на сервере | Да (виден владельцу и собеседникам по радио) |
| **MID** | ID сообщения в Radio Chat. | `короткий адрес отправителя (4 Б) + счётчик (4 Б)` — поля `src` + `counter` радиокадра | Устройство/приложение отправителя, монотонно | Служебный (в UI — в деталях сообщения) |

Решения:

- **Неизменяемость UID:** в БД колонка без операций UPDATE в коде, плюс триггер, запрещающий изменение; в API нет эндпоинта для смены.
- **Внутренний ключ БД** — отдельный суррогатный ключ (bigint), наружу не выходит. Это внутренняя деталь, не четвёртый ID: пользователь видит только UID.
- **Поиск — только по точному UID.** По номеру телефона и по имени не ищем. Защита от перебора: 40 бит пространства + rate limit на поиск.
- **MID** одновременно служит для защиты от повтора (счётчик), для подтверждений доставки по радио и для отсева дублей при будущей ретрансляции.
- **Не дублируются и не конфликтуют:** уникальные индексы в БД; разные префиксы (`NX-`, `D-`) — по строке сразу понятно, что это за ID.
- **DID привязан к криптографическому ключу**, а не к MAC-адресу (MAC ESP32 читается и подделывается). Устройство генерирует ключевую пару при первом запуске, приватный ключ не покидает ESP32 (в перспективе — flash encryption + secure boot). Подменить устройство = подделать подпись Ed25519.
- **Привязка UID ↔ DID:** приложение подключается по BLE → сервер выдаёт случайный challenge → устройство подписывает → сервер проверяет подпись и записывает «DID принадлежит UID». Одно устройство — один владелец; передача — через явную отвязку.
- **В эфире** используется 4-байтовый короткий адрес (из DID) для экономии места; полный DID и ключи сверяются по локальному справочнику, полученному при привязке/обмене контактами.

## 5. Регистрация, сессии, восстановление

1. Номер в формате E.164 → `POST /auth/otp/request`.
2. Сервер генерирует 6-значный код (CSPRNG), хранит **только HMAC(код)**, TTL 5 мин, максимум 5 попыток; rate limit на номер и IP.
3. `POST /auth/otp/verify` → создаётся аккаунт (если новый) + сессия.
4. Сессия: короткий access-токен (15 мин) + refresh-токен с ротацией (в БД — только хэш), привязан к установке приложения. Экран «Активные сессии» с отзывом — в настройках.
5. Восстановление: повторная верификация номера.
6. **PIN против перевыпуска SIM (утверждено).** Пользователь может включить в настройках PIN (4–6+ цифр). Если PIN включён, при входе по номеру с нового телефона сервер, помимо SMS-кода, требует PIN. Злоумышленник, перевыпустивший SIM-карту, получит SMS, но без PIN в аккаунт не войдёт.
   - PIN хранится только как хэш **Argon2id** с солью; ограничение попыток (например, 10) с нарастающей блокировкой.
   - Если PIN забыт — вход возможен после периода ожидания (как у Signal, 7 дней без активности аккаунта); иначе аккаунт потерян навсегда. Точный срок — на обсуждение.
   - Сменить/отключить PIN можно только из уже авторизованной сессии.
7. Ключи E2EE хранятся только на устройстве; при переустановке история зашифрованных чатов без резервной копии не восстанавливается — это свойство E2EE, а не баг. Бэкап — отдельная задача на будущее.

## 6. Обычные чаты и Ghost Mode

- Сообщение = зашифрованный конверт `{id, from, to, ts, ciphertext}`. Сервер хранит его до доставки и удаляет после подтверждения.
- Статусы: `sending` (локально) → `sent` (сервер принял) → `delivered` (клиент адресата подтвердил приём) → `read` (клиент адресата отправил квитанцию прочтения).
- **Ghost Mode — на серверном уровне:**
  - квитанция `read` — это отдельное явное событие, которое генерирует *только* клиент; сервер никогда не выводит «прочитано» косвенно (из факта загрузки сообщений, открытия чата и т.п.);
  - при включённом Ghost Mode клиент квитанцию не отправляет, а сервер дополнительно хранит флаг `ghost_mode` пользователя (глобально и по чатам) и **отбрасывает** любые `read`-события от него — даже от модифицированного/старого клиента или из-за гонки;
  - `delivered` при этом продолжает работать (иначе собеседник видит «не доставлено» — это отдельный вопрос, можно обсудить).
- **Сквозное шифрование во всех чатах по умолчанию.** Важное отличие от Telegram: у Telegram обычные чаты шифруются только между телефоном и сервером (сервер может читать), а сквозное — только в «секретных чатах». В Nexlock каждый чат работает как секретный чат Telegram: сервер не может прочитать ни одно сообщение. Протокол — Signal Protocol (стандарт отрасли, его же используют WhatsApp и Signal), а не MTProto Telegram, т.к. ТЗ требует проверенных протоколов. Следствие: история не хранится на сервере «в облаке», как у обычных чатов Telegram.
- Поиск пользователей — только по UID. Поиск по чатам — локальный (на телефоне, по расшифрованной истории в SQLite), т.к. сервер содержимого не видит.
- Медиа — в следующих версиях (зашифрованные blob'ы в объектном хранилище).

## 7. Radio Chat

### Цепочка

`Приложение (шифрует) → BLE → ESP32 (очередь, кадрирование) → UART → E22 → эфир → E22 → ESP32 → BLE → Приложение (расшифровывает)`

Шифрование и ключи — **на телефоне**; устройство — доверенный, но «слепой» модем. Компрометация устройства не раскрывает переписку.

### Радиокадр (черновик, v1)

```
| ver 1B | type 1B | src 4B | dst 4B | counter 4B | ttl/hops 1B | flags 1B | ciphertext … | tag 16B |
                  └──────── MID = src + counter ────────┘
```

- Заголовок (16 байт) — AAD, т.е. защищён от изменения.
- Nonce (12 байт) = `src || counter` + константа — не передаётся, вычисляется.
- Ключ пары = HKDF(X25519(ключ_A, ключ_B)) — ключи устройств/пользователей обмениваются заранее через интернет или QR.
- **Защита от повтора:** монотонный `counter` отправителя + скользящее окно на приёме; счётчик сохраняется во flash.
- `ttl/hops` заложен под будущую ретрансляцию (этап 5), сейчас не используется.
- Длинные сообщения — фрагментация (тип кадра `FRAG`).
- Известное ограничение v1: статический ключ пары без forward secrecy. Улучшение — на этапе 5.

### Демо-режим

Пока нет железа, Radio Chat работает через `DemoRadioTransport` — **локальный симулятор внутри приложения** (петля / эмуляция второго устройства на том же телефоне). Экран при этом постоянно показывает плашку **«ДЕМО: радиосвязь не используется»**. Через интернет радиосообщения не отправляются никогда.

### Юридическое

E22-400T30D — модуль 410–493 МГц, до 30 dBm (1 Вт). В РФ безлицензионное использование полосы 433,075–434,79 МГц ограничено малой мощностью (порядка 10 мВт) — **1 Вт без разрешения использовать нельзя**. Мощность и частота будут конфигурируемыми в прошивке с безопасными значениями по умолчанию; актуальные нормы региона эксплуатации нужно проверить до полевых испытаний.

## 8. Безопасность — сводка

| Требование | Решение |
|---|---|
| Защищённая авторизация | OTP (HMAC в БД, TTL, лимиты), без паролей |
| Хранение данных | Ключи — Keystore/Keychain; на сервере — минимум данных, токены и коды только хэшами |
| Шифрование канала | TLS 1.3, HSTS; certificate pinning — опционально |
| E2EE | Signal Protocol (libsignal) |
| Защита DID / от подмены устройств | DID = хэш ключа Ed25519, challenge-response при привязке и подключении по BLE |
| Replay | Signal — встроено; радио — counter + окно |
| Сессии | Короткий access + ротируемый refresh, отзыв, список устройств |

## 10. Что требует сервера, а что нет

**Нужен сервер:**
- отправка SMS и проверка OTP, создание аккаунтов, сессии;
- выдача UID, реестр DID и привязка устройств к владельцам;
- поиск пользователей;
- ретрансляция и временное хранение зашифрованных сообщений, статусы доставки/прочтения (и серверная часть Ghost Mode);
- раздача публичных ключей (prekeys) для Signal Protocol;
- push-уведомления (FCM/APNs);
- в будущем — хранилище зашифрованных медиа.

**Сервер не нужен:**
- сама передача Radio Chat между устройствами;
- шифрование/расшифровка (всегда на клиенте);
- локальная история, поиск по чатам;
- демо-режим радио.

---

## 11. Что входит в первую версию (MVP = этапы 1–2)

- Splash, приветствие, регистрация по номеру + OTP, главная навигация, космический стиль.
- Список чатов, личная переписка (текст), время, статусы sent/delivered/read, профили, поиск по UID и по чатам, уведомления.
- Ghost Mode (клиент + сервер).
- Radio Chat — только интерфейс в **демо-режиме** с плашкой.

Не входит в MVP: медиа, реальная радиосвязь, ретрансляция, бэкапы.

## 14. Хостинг сервера

GitHub и облако выполняют разные задачи:

- **GitHub** — хранилище исходного кода и истории изменений. Работа Claude Code идёт во временном контейнере, который удаляется после сессии; код, не отправленный в репозиторий, теряется.
- **Облако (Google Cloud или другое)** — где *запущен* сервер Nexlock, к которому подключаются приложения пользователей.

Вариант на Google Cloud:

| Компонент | Сервис |
|---|---|
| Сервер (Fastify + WebSocket) | Cloud Run |
| PostgreSQL | Cloud SQL for PostgreSQL |
| Redis | Memorystore (дорогой минимум) — на старте можно заменить на Postgres |
| Push Android | Firebase Cloud Messaging |
| Секреты (ключ HMAC, ключи SMS) | Secret Manager |

Аккаунт и оплату облака создаёт владелец проекта; Claude не может открыть облачный аккаунт сам. Ограничение: Google Cloud не принимает новых клиентов из РФ (с 2022 г.); в этом случае альтернатива — Yandex Cloud (Serverless Containers, Managed PostgreSQL) — сервер переносится без изменений кода, т.к. упакован в Docker.

Для этапа 1 облако не требуется: сервер запускается локально через `docker compose`. Выбор облака нужен к концу этапа 2 (когда два реальных телефона должны переписываться).
